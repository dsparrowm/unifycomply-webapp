0. How to read this

Every endpoint card carries a status badge and the credential types it accepts:

LIVE endpoint exists, was called for this guide, and behaves as documented. PARTIAL endpoint works, but one

or more fields are always null / empty by design today, or a dependency is missing in some environments.

NOT BUILT nothing exists yet.

SESSION a signed-in user's JWT. API KEY an app-scoped secret sk_… . PUBLIC no credentials.

Method colours: GET blue, POST green, PUT purple, PATCH amber, DELETE red. Paths are shown with the /v1

prefix exactly as you send them.

1. Fundamentals — auth, headers, envelope, errors, limits

TWO CREDENTIAL TYPES

Credential How to send it Use it for

Session

JWT

Authorization: Bearer <token> from sign-in / onboarding /

refresh, plus x-app-id: <appId> to pick which of the tenant's

apps you act on (omit → the tenant's default app)

Everything a human does in the dashboard:

settings, team, investigations, verification

review tabs.

API key Authorization: Bearer sk_<domain>-<random> . App and

domain are baked into the key; x-app-id is ignored.

Server-to-server integration: customers,

documents, verifications, transactions,

webhooks, dashboard reads.

Routes guarded by CombinedAuthGuard accept either credential. Routes guarded only by PermissionsGuard are

session-only — an API key gets 401 Unauthorized , not 403 (see 1.4). Session routes also check the signed-in

user's role permissions ( dashboard:access , tenant-settings:update , case:resolve , case:escalate ,

pnd:manage , sar:file , …); a role without the permission gets 403.

API-KEY SCOPES

Scope Grants

customers:read / customers:write Customer roster, profile CRUD, account purpose, TM subscription, flags,

approve/reject, offboard

documents:write Uploading or replacing documents (customer and shareholder)

verifications:read /

verifications:write

Starting/reading verifications, available checks, the /dashboard/* reads

webhooks:read / webhooks:write Reading webhook deliveries / requeueing one

transactions:read /

transactions:write

Transaction ingestion and reads, TM dashboard/queues, account statement

A key missing the scope a route needs gets 403 (the key is valid, it just isn't allowed).

HEADERS & CORS

Allowed request headers: Authorization , Content-Type , x-app-id . Allowed methods: GET POST PUT DELETE

PATCH OPTIONS . Your origin must be in core-platform's CORS_ORIGINS . Bodies are application/json ; files travel as

base64 data URIs inside JSON (never multipart).

RESPONSE ENVELOPE

{

"status": true, // false on any error

"message": "…", // human-readable, safe to toast

"data": { … } | [ … ] | null,

"meta"?: { "totalItems", "itemsCount", "itemsPerPage", "totalPages", "currentPage" }, // paginated lists

only

"summary"?: { … } // list screens that also need tile counts (TM queues, PND, SAR,

statement)

}

Paginated lists accept page (1-based) and limit (default 20).

ERRORS — REAL EXAMPLES

400 — validation failure (one message string listing every failed rule)

// request — PUT /v1/tenants/apps/1f62a4c6854e404385bf807eea9a7b5e/notification-preferences

{"eventCallbackUrl": "http://localhost:4999/webhooks/unifycomply", "webhookEnabled": true}

// response — HTTP 400

{"status": false, "message": "eventCallbackUrl must be a URL address"}

401 — bad credentials

// response — HTTP 401

{"status": false, "message": "User authentication failed. Invalid username or password"}

401 — API key on a session-only route

// response — HTTP 401

{"status": false, "message": "Unauthorized"}

404 — unknown id

// response — HTTP 404

{

"status": false,

"message": "No SAR filing found with a matching id: 00000000000000000000000000000000"

}

429 — rate limited

// response — HTTP 429

{"status": false, "message": "ThrottlerException: Too Many Requests", "data": null}

Rate limits are per client and stacked: 10 requests / second, 40 / 10 seconds, 200 / minute. A burst (e.g. firing every

dashboard tile plus a table at once) can hit the 10/s window — fetch lazily, debounce search inputs, and retry 429s with

backoff.

DOMAIN — SANDBOX VS PRODUCTION

Every tenant has two isolated domains. A sandbox customer is invisible to a production request. API keys are bound

to one domain at issue ( sk_sandbox-… / sk_production-… ). A session switches with POST

/v1/tenants/settings/domain/switch (§6.4), which re-issues the token. Sandbox calls deterministic provider

simulators — nothing billed, nothing sent to a real watchlist; the AML simulator flags any name containing "sanction"

or "pep".

2.9 Google sign-in LIVE PUBLIC

GET /v1/auth/google/sign-in?redirect=<your-callback-url>

GET /v1/auth/google/callback

POST /v1/auth/sign-in/intent

Navigate the browser (not fetch ) to /v1/auth/google/sign-in . It answers 302 to Google's consent screen

(captured: HTTP 302 → https://accounts.google.com/o/oauth2/v2/auth?… ). Google returns to

/v1/auth/google/callback , which redirects to your redirect URL with a one-time intent . Exchange it:

POST /v1/auth/sign-in/intent?platform=app

{ "intent": "<intent from the redirect>" }

// → same session shape as §2.3

Not captured live. The callback and intent exchange need a real Google account; shapes are from the controller.

webhook secret. Verify against the raw body (not re-serialised JSON), compare in constant time, and reject

stale timestamps.

17. What's left — known gaps

Real behaviour observed while building this guide. None blocks integration, but each needs a deliberate UI state.

AI SAR drafting returns a bare 500 when no AI key is configured

provider-gateway needs ANTHROPIC_API_KEY . Without it, §15.6 messages fail with "Internal server error" instead of a

clear 503. Configure the key per environment and/or map this failure to a friendly error.

Clean transactions appear in no queue

A transaction that matches no rule gets category: null , so TM Not-Blocked ("cleared for processing") never lists it

(§14.2).

Investigation enums are not in the public option registry

Case resolution types, actions-taken, PND resolution types, entity type and investigation risk level must be hardcoded

from §15–§16 until they are registered in /v1/public/misc/options .

Four seeded detection rules never fire

High ML Fraud Probability, Large Withdrawal Pattern, New Device High Amount and Velocity Spike need

windowed/velocity evaluation that does not exist yet (§13.1).

Three Re-KYC triggers are no-ops

high-risk-jurisdiction , forged-id , immigration-check (§13.4).

Always-null fields

monthlyVolume (§14.1), customer.maskedAccount and riskNarrative (§12.3), every device-information field

(§10.4), most liveness detail (§10.5), director nationality/ID and share class (§10.7), extractedInformation (§10.1).

Flags only come from ongoing monitoring

Onboarding runs never raise flags (§8.7); the flag workflow UI will look empty until a post-onboarding AML observation

arrives.

Webhooks cover two events

Only workflow.verified and workflow.failed (engine or manual decision). Re-KYC escalations to in-review ,

transaction alerts and investigation actions are not pushed — poll the relevant endpoints.

Source of truth: core-platform controllers under apps/core-platform/src/**/controllers , live Swagger at /v1/docs . Companion

docs: docs/ui-contracts/transaction-monitoring-endpoints.md , docs/ui-contracts/verification-detail-

tabs.md , docs/rekyc-tm-rules-rollout.md .
