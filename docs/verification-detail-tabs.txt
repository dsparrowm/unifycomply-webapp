Verification detail tabs — frontend integration guide
Recorded 2026-09-15. Covers the eleven endpoints behind a verification's review screen: GET
/v1/verifications/kyc/:workflowId/* (five tabs) and GET
/v1/verifications/kyb/:workflowId/* (six tabs). Companion to verification-list-endpoints.md
(the list/queue view these tabs are drilled into from) and api-integration-guide.md (the full API
reference).
Auth — read this before wiring anything up
Session (JWT) only. These routes are guarded by PermissionsGuard({ allow:
['dashboard:access'] }) — no CombinedAuthGuard, no API key path at all. A request authenticated
with a tenant API key gets a 401, not a 403 — the guard doesn't recognize the credential as a session, full
stop.
This is deliberate, not an oversight: a document's signed download URL and a director's identity detail are
exactly the kind of customer-identifying material an API-key integration has no business pulling in bulk. If
your frontend currently drives its other verification screens off an API key (the way the test console's
"Verifications" list can), these eleven routes need your app's own signed-in session instead — same
Authorization: Bearer <token> header, just a session token from POST /auth/sign-in, not
sk_....
A workflow requested through the wrong profile's path — a business workflow via
/verifications/kyc/..., or an individual one via /verifications/kyb/ ... — 404s. The path
doesn't just filter, it asserts.
Every route returns the usual envelope: { status, message, data }. No meta — nothing here is
paginated.

      "providerReference": null,
      "attempts": 1,
      "completedAt": "2026-09-14T22:46:40.144Z"
    }

}
Only the sanctions-/pep-screening tasks — everything else on the run is excluded, this tab isn't a general
task list. No per-list breakdown (OFAC / UN / EU / UK HMT rows) and no separate watchlist/warning
sections — that's reasons[]'s evidence.datasetsSearched, not a mapped shape. As of the multi-
provider change, a single task's reasons[] can already contain entries from more than one provider with
no per-reason attribution — don't assume one reasons array means one provider call.

Read this before building a real liveness screen. The dedicated liveness provider capability (matchScore,
livenessPassed, a per-check breakdown of face detection / real person / no mask / eyes open / facing
camera, completion time, attempt count) exists in provider-gateway but is never actually invoked — a
selfie check runs through the same generic identity-lookup path as any other check today, confirmed
live. For most countries there's no identity type mapped to "selfie", so the task settles skipped and this
tab has nothing but that skip reason to show. matchScoreRate only ever gets a value on the rare path
where the generic identity check did run and returned field-match scores — it is not a biometric match
score. Don't build a liveness-detail UI expecting the rich mockup data (confidence %, checks-performed list,
attempts, seconds) — none of it exists server-side yet.

compliance-checks
{
  "tasks": [
    {
      "id": "...",
      "verificationType": "sanctions-screening",
      "outcome": "passed",
      "reasons": [ /* ... */ ],
      "providerKey": "sandbox-aml"
    }
  ]
}
The business entity's own sanctions-/pep-screening tasks only — filtered to shareholderId ===
null. A director's screening result never appears here; it's exclusively on directors-officers. If a
screen needs "every AML check on this run, business and directors together," it has to combine both tabs
client-side — there's no combined endpoint.
Building the tab UI
Both controllers return every tab as a flat, independent GET — there's no "give me the whole detail page in
one call." Fetch each tab lazily as the user opens it (the test console does exactly this, one request per tab
click, cached for the life of the page) rather than firing all five or six requests on page load.
Gate which tab set you request on the workflow's own profileType — pull it from GET
/verifications/:workflowId (or the list row) first, then hit kyc/... or kyb/... accordingly. Hitting
the wrong path 404s.
